# Database Schema Design · 数据库 Schema 设计

## 核心思想
Schema 是系统的数据骨架——设计不当，后续所有查询、扩展、维护都会付出代价。好的 Schema 设计在规范化与查询性能之间取得平衡，通过显式的迁移策略保证演进安全，通过索引策略保证查询效率。Schema 变更是不可逆的，设计阶段投入的时间回报最高。

## 适用场景
- 新项目数据模型设计
- 现有 Schema 重构（规范化/反规范化）
- 数据库迁移策略制定
- 查询性能优化（索引设计）

## 关键步骤

### 1. 数据建模

**实体关系分析**
- 识别核心实体和关系（1:1 / 1:N / M:N）
- 确定主键策略（自增 ID / UUID / ULID / Snowflake ID）
- M:N 关系需要中间表（关联表）
- 区分强实体和弱实体（弱实体依赖父实体存在）

**规范化 vs 反规范化**
- **3NF 规范化**（默认）：消除传递依赖，减少更新异常
- **反规范化**（性能驱动）：
  - 冗余字段：避免频繁 JOIN（如订单表冗余用户名字段）
  - 聚合表/物化视图：预计算高频查询结果
  - 原则：只在查询瓶颈处反规范化，写入时维护一致性

### 2. 索引策略

**索引类型选择**
| 场景 | 索引类型 | 说明 |
| --- | --- | --- |
| 等值查询 | B-Tree（默认） | `WHERE user_id = ?` |
| 范围查询 | B-Tree | `WHERE created_at > ?` |
| 全文搜索 | Full-Text / 倒排索引 | `WHERE content LIKE '%keyword%'` |
| JSON/数组查询 | GIN | PostgreSQL JSONB / 数组字段 |
| 地理空间 | GiST / R-Tree | 经纬度范围查询 |
| 高基数唯一 | Hash | 等值查询，空间换时间 |

**索引原则**
1. 为 WHERE / JOIN / ORDER BY 高频列建索引
2. 复合索引遵循最左前缀原则——高选择性列在前
3. 覆盖索引（Covering Index）避免回表
4. 避免过度索引——每个索引增加写入成本和存储空间
5. 定期审查未使用索引并清理

### 3. 迁移策略

**迁移原则**
- 所有 Schema 变更通过迁移脚本管理，禁止手动 DDL
- 迁移必须可逆（up + down）
- 迁移脚本纳入版本控制
- 生产环境迁移必须向后兼容（不中断服务）

**安全变更模式**
| 变更类型 | 安全做法 |
| --- | --- |
| 加列 | 允许 NULL 或有默认值，分步：加列 → 双写 → 迁移数据 → 切换读 → 删旧列 |
| 删列 | 先停止写入 → 确认无读取 → 删除（至少跨 2 个发布周期） |
| 改列类型 | 加新列 → 双写 → 迁移数据 → 切换读 → 删旧列 |
| 加索引 | 使用 `CREATE INDEX CONCURRENTLY`（PostgreSQL）避免锁表 |
| 重命名 | 加新名 → 双写 → 切换读 → 删旧名 |

### 4. 数据完整性
- 外键约束保证引用完整性（权衡：微服务间通常不用外键，靠应用层保证）
- CHECK 约束限制字段值范围
- UNIQUE 约束防止重复
- NOT NULL 除非业务允许为空
- 软删除 vs 硬删除：审计需求选软删除（`deleted_at` 字段）
