# Microservices Patterns · 微服务模式

## 核心思想
微服务不是"把单体拆成 100 个小服务"——它是关于独立部署、独立团队、独立数据源的架构风格。每个模式解决一个具体的分布式系统问题，但也有对应的代价。选择模式前必须同时评估收益和代价，避免"为了微服务而微服务"。

## 适用场景
- 单体系统拆分策略制定
- 分布式系统的数据一致性设计
- 服务间通信模式选择
- 微服务治理（发现、熔断、限流）

## 关键步骤

### 1. 拆分策略

**何时拆分**：
- 团队规模超过 2 pizza team（>10 人），需要独立交付
- 模块的扩展需求不同（计算密集 vs I/O 密集）
- 模块的变更频率差异大
- 模块需要不同的技术栈

**拆分边界**：
- 按业务领域（DDD 限界上下文）拆分，而非技术层
- 每个服务拥有自己的数据存储（Database per Service）
- 服务间通过 API 通信，不共享数据库表

### 2. 数据一致性模式

| 模式 | 一致性 | 复杂度 | 适用场景 |
| --- | --- | --- | --- |
| **Saga（编排式）** | 最终一致 | 中 | 3-5 个服务协调 |
| **Saga（协同式）** | 最终一致 | 高 | 服务间松耦合，事件驱动 |
| **Outbox Pattern** | 最终一致 | 低 | 保证本地事务 + 消息发送原子性 |
| **CQRS** | 读写分离 | 中 | 读写负载差异大 |
| **Event Sourcing** | 完全可追溯 | 高 | 审计要求高、需要时间旅行 |

**Saga 模式详解**：
- 每个本地事务发布事件，触发下一个服务的事务
- 每个步骤有对应的补偿事务（Compensating Transaction）
- 失败时按反向顺序执行补偿，实现最终一致性
- 使用 Outbox Pattern 保证"本地事务 + 消息发送"的原子性

### 3. 服务间通信

| 模式 | 同步/异步 | 耦合度 | 适用场景 |
| --- | --- | --- | --- |
| **REST/HTTP** | 同步 | 中 | 简单请求-响应 |
| **gRPC** | 同步 | 低 | 高性能内部通信 |
| **消息队列** | 异步 | 低 | 解耦、削峰、事件通知 |
| **事件总线** | 异步 | 低 | 多服务订阅同一事件 |

### 4. 服务治理

**服务发现**：
- 客户端发现（Consul / etcd 注册）
- 服务端发现（Load Balancer 代理）
- DNS 发现（Kubernetes Service）

**弹性模式**：
- **熔断器（Circuit Breaker）**：下游故障时快速失败，避免级联故障
- **重试 + 退避**：瞬时故障自动重试，指数退避避免雪崩
- **限流（Rate Limiting）**：保护服务不被过载
- **超时**：每个调用设置合理超时，避免资源长期占用
- **舱壁隔离（Bulkhead）**：隔离不同调用的资源池，一个失败不影响其他

### 5. 反模式警告
- **分布式单体**：服务间强耦合，部署仍需同步 → 没真正拆分
- **共享数据库**：多个服务直接访问同一个数据库 → 违反 Database per Service
- **跨服务事务**：用分布式事务（2PC/3PC）而非 Saga → 性能和可用性灾难
- **过度拆分**：服务粒度太细，运维成本远超收益
