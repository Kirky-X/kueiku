# Code Review Checklist · 代码审查检查清单

## 核心思想
系统化审查代码变更，覆盖安全、架构、性能、可维护性四个维度。每个维度有明确的检查项和严重级别定义，将"凭感觉 review"变成可审计的清单驱动审查。审查目的不仅是找 bug，更是知识传递和代码所有权共享。

## 适用场景
- PR/MR 合并前的质量门禁
- 重构后的变更影响评估
- 新人代码的质量保障
- 安全敏感模块的变更审查

## 关键步骤

### 审查维度与检查项

**1. 安全维度（CRITICAL 级）**
- 是否有硬编码密钥/凭证/Token？
- 用户输入是否经过验证和转义（SQL 注入/XSS/命令注入）？
- 权限检查是否完整（越权/水平越权）？
- 敏感数据是否加密存储和传输？
- 依赖是否引入已知漏洞？

**2. 架构维度（HIGH 级）**
- 变更是否符合现有架构分层和模块边界？
- 是否引入不必要的依赖或循环依赖？
- 接口变更是否向后兼容？
- 是否有重复实现已有功能？
- 错误处理是否统一且完整？

**3. 性能维度（MEDIUM 级）**
- 是否有 N+1 查询或不必要的循环内 I/O？
- 大数据集是否使用分页/流式处理？
- 是否有不必要的内存分配或对象拷贝？
- 缓存策略是否合理（过期/失效/穿透）？
- 并发场景是否有竞态条件？

**4. 可维护性维度（LOW 级）**
- 命名是否清晰表达意图？
- 函数/方法是否职责单一、长度合理？
- 复杂逻辑是否有注释说明"为什么"而非"做了什么"？
- 测试是否覆盖核心逻辑和边界条件？
- 代码风格是否与项目惯例一致？

### 审查流程
1. 先读 PR 描述和关联 issue，理解变更意图
2. 看测试变更，理解预期行为变化
3. 按 安全→架构→性能→可维护性 顺序逐维度检查
4. 每个发现标注严重级别：CRITICAL / HIGH / MEDIUM / LOW
5. CRITICAL/HIGH 必须修复方可合并；MEDIUM 建议修复；LOW 可留 follow-up
6. 审查结果必须包含：通过/需修改/阻断 + 具体检查项反馈
