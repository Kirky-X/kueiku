# User Stories

## Core Idea
Use the "As a [role], I want [feature], so that [benefit]" format to transform requirements from "what the system must do" to "what the user wants to accomplish." Combined with the 3 C's (Card/Conversation/Confirmation) and the INVEST criteria, this prevents backlogs from becoming unactionable feature lists.

## Use Cases
- Agile development team backlog management
- Requirements documents need to shift from a feature perspective to a user perspective
- Stories are too large or too small to plan sprints effectively

## Key Steps
1. Write the story: As a [role], I want [capability], so that [value]
2. Apply the 3 C's:
   - Card: Story card (one sentence, can be written on a sticky note)
   - Conversation: Discussion around the card (details emerge during conversation, not all pre-defined)
   - Confirmation: Acceptance criteria ("what counts as done" — testable)
3. Validate quality with INVEST:
   - Independent (not dependent on other stories)
   - Negotiable (details can be discussed)
   - Valuable (clear value to the user)
   - Estimable (effort can be estimated)
   - Small (completable within one sprint)
   - Testable (has clear acceptance criteria)
4. Split or rewrite stories that don't meet the criteria
5. Confirm acceptance criteria are defined for each story during sprint planning

## Source
Standard agile practice; 3 C's by Ron Jeffries, INVEST by Bill Wake
